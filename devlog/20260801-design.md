# Salt Spring ontology extractor — design (Claude)

An experiment: read Salt Spring Island news feeds on an ongoing basis, use an
LLM at runtime to pluck out the concepts (entities, their prototypes, their
relationships), de-duplicate references, and render the accumulating knowledge
graph on a public page — map + enumerations + a force-directed graph.

Fuel: the `cortes` and `saltspring` demos (bus/store/dedupe/ECS `item`
schema, island perimeter, gazetteer) and Anselm's ontology-extractor work at
github.com/orbitalfoundation.

## Data model — one collection, ECS + prototypes

Every node is an **entity**: an id plus remixable **components**. Kind is a
coarse bucket but is also inferable from which components decorate the entity
(has `relation` → it's an edge; has `location` → it's placeable; its
`prototype` says it's a Road). Richer formalism → more views, per Anselm.

```
entity {
  id,                       // 'ent:<sha1>' — stable
  kind: 'instance' | 'prototype' | 'relation',
  components: {
    metadata:   { name, aliases[], description },
    prototype:  { of: [protoId, …] },     // prototype-based classification
    location:   { lat, lon, label, method },
    relation:   { predicate, from, to },  // present iff it's an edge
    provenance: { sources:[{url,title,date,quote}], mentions, confidence,
                  firstSeen, lastSeen },
    // open-ended kind-specific buckets added as extraction finds them:
    // person{…} org{…} road{status,…} event{status,when,…} …
  }
}
```

**Prototype-based, not class-based.** A "prototype" is itself an entity
(`kind:'prototype'`, e.g. *Road*, *Person*, *Government body*, *Vehicle*).
Instances link to one or more prototypes via `components.prototype.of`.
Prototypes can themselves have prototypes (*Road* → *Infrastructure*), so the
abstraction is an open graph you can extend at runtime, not a fixed class tree.
Seeded with a handful of base prototypes; the extractor proposes new ones and
they are deduped like anything else.

## The relationships question (Anselm asked: separate table, or a property?)

**Decision: relationships are first-class entities** — edges are entities
decorated with a `relation` component (`{predicate, from, to}`). Not embedded
properties, not a separate table.

Why edges-as-entities wins *here specifically*:
- **Provenance.** Extraction is noisy; every edge must remember which article
  asserted it, with the sentence, and how confident we were. An embedded
  property can't carry that cleanly; a reified edge can.
- **Deduplication.** The same claim ("Council ↔ Fulford-Ganges Road repair")
  appears across articles. Edges dedupe through the *exact same* path as
  nodes — one code path.
- **Time.** "Road is under repair" is a time-bound assertion. An edge entity
  has firstSeen/lastSeen and can carry a status without touching either node.
- **Uniformity.** Keeps the single collection Anselm likes; relationships
  become just another view over `entities`, queryable the same way.

The trade-off: an embedded property (e.g. `person.memberships[]`) is cheaper
to read and fine for *stable, load-bearing* relations you always want with the
node. So the rule: **stable structural facts can be embedded components;
extracted, sourced, uncertain claims are edge entities.** For this experiment
everything the LLM extracts is an edge entity, because all of it is sourced
and uncertain.

## Pipeline (LLM at runtime)

1. **Fetch** article text (strip HTML).
2. **Extract** — one structured-output call to a local model (ollama
   `gpt-oss:120b` on this box; Anthropic API if a key is present) → JSON:
   entities (name, proposed prototype, kind hint, description, optional
   location, supporting quote) + relations (from, predicate, to, quote).
3. **Resolve / dedupe** — normalize names; match against existing entities by
   name/alias, and by `nomic-embed-text` cosine similarity for fuzzy merges
   ("Salt Spring", "the island", "SSI"). Merge provenance, bump mentions,
   update lastSeen. Prototypes and relations resolve through the same path.
4. **Store** — mongo (survives redeploy) or JSON fallback; emit a `graph.json`
   snapshot for the front end.

## Where it runs (important architectural fact)

The exe.dev VM has no LLM. **This box does, and is the persistent worker.**
So: the extractor runs *here* on a schedule, accumulates the graph, and writes
a snapshot into the app; exe.dev serves the read-only visualization and
autodeploys when the snapshot is pushed. Ongoing/persistent ingestion lives on
this box; the public page is the always-fresh result. Honest and matches the
infrastructure.

## Visualization

Four views over one graph, cross-linked by selection:
- **Force-directed graph** (d3-force + SVG): instance nodes colored by
  prototype, sized by mentions/degree; prototype hubs drawn larger with dashed
  is-a links so the prototype classification is *visible as structure*; edges
  labeled by predicate on hover.
- **Map** (maplibre) of the island with the perimeter; located entities as
  markers; selection shared with the graph.
- **Enumerations** — three panels: Prototypes (abstract primitives + counts),
  Components (trait buckets in use + counts), Entities (instances, filterable).
- **Detail** — selected entity's components, prototype chain, provenance
  quotes with source links, and its relations.

## Scope for the first shot

Real extraction over ~10 real Driftwood articles → real graph → the four
views → deployed. Not yet: live continuous crawl of many sources, entity
editing/curation, embeddings-based merge review UI. Those are next.
